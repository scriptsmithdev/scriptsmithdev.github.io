Kubernetes Deployments: Moving Beyond the Pod

September 11, 2026

After getting familiar with Kubernetes Pods, the next step was understanding how Kubernetes manages applications beyond a single running container. This led me to Kubernetes Deployments and ReplicaSets.

What I Learned

I learned that a Kubernetes Deployment provides a declarative way to manage application workloads. Instead of manually creating individual Pods, I can describe the desired state of an application and allow Kubernetes to maintain that state.

A Deployment manages ReplicaSets, and ReplicaSets are responsible for maintaining the desired number of Pods. This creates a useful relationship between Deployments, ReplicaSets, and Pods.

What I Did

I created a Kubernetes Deployment and used kubectl to inspect the resources Kubernetes created. 

kubectl get deployments
kubectl get replicasets
kubectl get pods

I also experimented with scaling the application and examined how Kubernetes responded by creating or removing Pods to match the desired replica count. 

kubectl scale deployment nginx --replicas=3
kubectl get pods

Understanding Rollouts

One of the most useful features I explored was the Deployment rollout mechanism. Deployments allow application versions to be updated gradually rather than replacing every Pod at once.

I used commands such as: 

kubectl rollout status deployment/nginx
kubectl rollout history deployment/nginx

This helped me understand how Kubernetes keeps track of different Deployment revisions.

The Problem

The main challenge was understanding the difference between a Pod, a ReplicaSet, and a Deployment. At first, these resources seemed to perform similar jobs.

How I Solved It

I solved this by inspecting each resource independently using kubectl. Looking at the resources together made the hierarchy much clearer.

The basic model I now understand is: 

Deployment
    |
    v
ReplicaSet
    |
    v
Pods

The Deployment manages the desired application state, the ReplicaSet maintains the required number of Pods, and the Pods run the actual application containers.

Key Takeaways

  • Deployments provide declarative application management.
  • Deployments manage ReplicaSets.
  • ReplicaSets maintain the desired number of Pods.
  • Deployments support rolling updates.
  • Deployment history can be inspected with kubectl.
  • Understanding the relationship between resources makes Kubernetes much easier to reason about.

What I Want to Explore Next

My next step is to go deeper into Kubernetes rolling updates, rollout strategies, rollback procedures, and how these concepts fit into a CI/CD pipeline.
