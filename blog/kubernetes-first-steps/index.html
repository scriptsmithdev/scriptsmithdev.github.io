Kubernetes: My First Steps into Container Orchestration

August 2026 · Felix Amoah · DevSecOps Engineering Journal

Kubernetes was one of the technologies I was most interested in reaching during my DevSecOps training. After working with Linux, Git, Docker, AWS, Terraform and CI/CD, I wanted to understand what happens when containerized applications need to be managed at a larger scale.

That led me to Kubernetes and, more specifically, Minikube. This article documents my first practical steps, the problems I encountered, and what I learned from working through them.

Lesson learned: Kubernetes is not simply "Docker with extra commands." It introduces a completely different way of thinking about application deployment, networking and infrastructure.

1. What is Kubernetes?

Kubernetes is an open-source container orchestration platform. Instead of manually managing individual containers, Kubernetes provides a system for deploying, scaling and managing containerized workloads.

The basic idea is simple: I describe the desired state of my application, and Kubernetes works to keep the cluster running in that state.

2. Why I Started with Minikube

Running a production Kubernetes cluster just for learning would be unnecessary. Minikube provides a lightweight local Kubernetes environment that makes it possible to experiment without needing a large cloud infrastructure setup.

I used Docker as the Minikube driver, allowing the Kubernetes environment to run locally through containers. 

minikube start --driver=docker

3. Understanding kubectl

One of the first tools I had to become comfortable with was kubectl. It is the command-line interface used to communicate with a Kubernetes cluster. 

kubectl get nodes
kubectl get pods
kubectl get deployments
kubectl get services

These commands quickly became essential for understanding what was happening inside the cluster.

4. My First Kubernetes Objects

Kubernetes applications are represented using different resources. Some of the first concepts I worked with were:

  • Pods
  • Deployments
  • Services
  • Namespaces
  • Nodes

Pods

A Pod is the smallest deployable unit in Kubernetes. It can contain one or more containers that share networking and storage resources.

Deployments

Deployments provide a higher-level way of managing Pods. They allow Kubernetes to maintain a desired number of application replicas and perform controlled updates.

Services

Services provide stable networking for applications running inside the cluster. This becomes especially important because Pods can be created, destroyed and replaced.

5. Working with Namespaces

I also started working with namespaces to separate workloads logically inside the cluster. 

kubectl get namespaces

kubectl create namespace dev

kubectl config set-context --current --namespace=dev

Using a dedicated namespace helped me understand how Kubernetes environments can be organized instead of placing everything into the default namespace.

6. Problems I Encountered

My Kubernetes journey was not completely smooth. I encountered connection errors where kubectl could no longer communicate with the Kubernetes API server. 

couldn't get current server API group list

dial tcp 127.0.0.1:xxxxx:
connect: connection refused

This taught me an important troubleshooting lesson: when kubectl fails, the first thing to investigate is not necessarily the application. The Kubernetes cluster, context and API server itself may be the problem.

I learned to check the Minikube profile and Kubernetes context before continuing with application-level troubleshooting. 

minikube profile list

minikube status

kubectl config get-contexts

kubectl config current-context

7. What Kubernetes Changed in My Thinking

Docker taught me how to package and run applications in containers. Kubernetes started teaching me how those containers can be managed as part of a larger system.

I began thinking less about "running a container" and more about desired state, replicas, networking, service discovery, orchestration and automated recovery.

8. What I Want to Learn Next

This is only the beginning of my Kubernetes journey. My next areas of focus are:

  1. Kubernetes networking
  2. ConfigMaps and Secrets
  3. Persistent storage
  4. Ingress
  5. Helm
  6. Kubernetes security
  7. Deploying applications through CI/CD

Final Thoughts

My first experience with Kubernetes reinforced something I have learned throughout my DevSecOps training: understanding the technology is only one part of the journey. The real learning happens when things break and I have to investigate why.

Kubernetes has given me another layer of infrastructure to understand, and I am looking forward to documenting the next stages of the journey here.
